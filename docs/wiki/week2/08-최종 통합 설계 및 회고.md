## 1. 최종 설계 범위

이 문서는 단계 1~7의 설계를 V1·V2 서비스 구조와 풀스택 연동 기준으로 통합한다. V3·수집 자동화·확장 운영의 설계도 함께 정의한다. 입력 처리, 곡 검색, 코퍼스 수명주기, 외부 API, 데이터 소유권, 배포와 관측 기준을 같은 흐름에서 설명한다.

머문음의 AI 서비스는 사용자 상황을 텍스트, 음성, 사진 또는 위치로 입력받아 실제 제공되는 음악을 추천한다.

제품 범위 | 주요 기능 | 상태
-- | -- | --
V1 | 텍스트 음악 추천, 음성 전사 | MVP 구현 범위
V2 | 풍경 사진 기반 음악 추천 | 정식 기능 개발·연동 기준
V3 | 위치·날씨·장소 기반 음악 추천 | 확장 설계

API 경로의 `/v1`은 제품 출시 단계가 아니라 API 계약 버전을 의미한다.

풀스택 연동은 [모델 API 설계](../week1/01-모델-API-설계.md)의 요청 필드·SSE 이벤트·오류 처리를 기준으로 한다. 모델 선정과 운영 설정은 API 계약을 유지하면서 관리한다. 성능·품질 수치는 6절의 평가 기준에 따라 기록한다.

## 2. 최종 서비스 아키텍처

### 현재 텍스트 추천 구현

```mermaid
flowchart LR
    INPUT[사용자 메시지·이전 대화] --> CLASSIFY[LLM 의도·검색 조건 추출]
    CLASSIFY --> EMBED[Gemini 3072차원 임베딩]
    EMBED --> SEARCH[pgvector 검색·조건 필터·중복 제거]
    SEARCH --> ANSWER[LLM 종합 안내]
    ANSWER --> SSE[text → tracks → done]
```

위 흐름은 지원 가능한 일반 추천의 성공 경로다. 곡별 이유 생성 호출과 추천·조회 응답의 `tracks[].reason`을 제거했다. 생성 LLM은 3회에서 2회로 감소했고, 임베딩 1회는 유지한다. 곡 선정·순서·종합 안내는 유지하며 실제 비용·지연 개선은 미측정이다. 빈 결과·조회·고정 안내는 별도 분기로 처리한다.

텍스트·사진 추천과 곡 조회 모두 공통 곡 응답에서 `reason`을 제거했다. 사진은 VLM 설명을 유지하며 검색 후 별도 생성 LLM을 호출하지 않는다. 아래 다이어그램은 V1·V2 구현을 기준으로 하며 위치 입력은 V3 설계다. 과거 CLAP 파일럿 결과는 설계 이력으로 구분한다. 연동에는 API 설계 문서의 응답 계약을 적용한다.

### 2.2 요청과 데이터의 흐름

Spring Backend가 사용자 인증과 권한을 확인한 뒤 AI 서버로 요청을 전달한다. 모바일 클라이언트는 AI 서버를 직접 호출하지 않는다. 회원·추천 기록·격자 저장은 Spring의 책임으로 설계했다. AI는 대화 맥락·최근 추천 ID를 LangGraph 메모리 체크포인터에, 사진 중복 예약·동시 처리 상태를 프로세스 메모리에 보관한다. 재시작 시 사라지며 워커·인스턴스 간에 공유되지 않는다. AI는 곡 메타데이터·임베딩 벡터·mood 태그를 담은 전용 PostgreSQL을 소유한다.

추천 요청은 입력 유형과 무관하게 같은 경로로 수렴한다. 텍스트·음성은 LLM이 확정된 문장을 한국어 검색 문장으로 재구성하고, 사진은 VLM이 풍경 분석과 함께 한국어 검색 문장을 직접 만든다. 위치는 날씨·주변 장소 컨텍스트에서 검색 문장을 만든다(V3 설계). 이 문장을 오디오와 텍스트를 같은 공간에 두는 Gemini 임베딩으로 질의 벡터로 만들고 pgvector로 상위 후보를 검색한다. 설계 단계에서는 영어 전용 CLAP과 영어 소리 서술을 썼으나, 현재 구현은 다국어를 지원하는 Gemini 임베딩으로 전환했다. 같은 프로세스에서 대화별 최근 추천 ID 100개를 검색에서 제외하고, 유사도 순 후보에서 동일 아티스트·제목의 중복을 제거한다. 별도의 아티스트 다양성 재정렬은 없으며, 선정된 곡의 mood 태그와 메타데이터를 LLM 입력에 보강해 한국어 추천 이유를 생성한다.

LLM은 검색 이전의 의도 분류·검색 문장 생성과 검색 이후의 이유·안내 문장 생성만 담당한다. 반환되는 곡은 AI PostgreSQL에 실재하는 `track_id`뿐이므로 모델이 임의로 생성한 곡을 카드에 추가하지 않는다. 생성된 설명의 사실성이나 링크의 현재 재생 가능성까지 보장하는 것은 아니다.

음성 입력은 전사 초안만 반환한다. 사용자가 채팅 입력창에서 확인·수정해 전송한 텍스트가 별도의 추천 요청으로 들어온다. 사진 입력은 기술 검증과 추천 적합성 판정을 먼저 수행해 판정과 사진 설명을 SSE로 먼저 보내고, VLM이 만든 검색 문장으로 검색을 진행한다.

### 2.3 곡 코퍼스 수명주기 — 운영 설계안

아래 사용자 검색 기반 적재·야간 배치 자동화는 현재 AI 추천 API의 구현 흐름이 아니다. 현재 온라인 추천·곡 조회는 DB를 사용하며, DB 조회 실패나 결과 없음으로 iTunes를 추가 호출하지 않는다.

추천 품질은 코퍼스가 무엇으로 구성되어 있는지에 직접 의존하므로, 수집을 상시 운영 파이프라인으로 확장하는 방안을 설계했다.

```mermaid
flowchart TB
    INIT[초기 수집: 아티스트 250명 기준] --> LOCAL[로컬 배치: 미리듣기 다운로드]
    LOCAL --> EMB[오디오 임베딩 · EffNet mood 태그]
    EMB --> DEL[오디오 파일 즉시 삭제]
    EMB --> READY[(AI PostgreSQL · ready)]

    USER[사용자 곡 검색] --> HIT{AI DB에 있는가}
    HIT -->|있음| USE[검색 결과 반환 · 격자 등록 가능]
    HIT -->|없음| CALL[iTunes API 조회]
    CALL --> USE2[격자 등록 가능 · 당일 추천에는 미등장]
    CALL --> PEND[(AI PostgreSQL · pending<br/>메타데이터만 적재)]

    PEND --> CRON[야간 배치: 미리듣기 확보 후 임베딩·태그 추출]
    CRON --> READY
    CRON --> NOPREV[(선택: no_preview 추천 후보 영구 제외)]
```

사용자가 지도에 등록할 곡을 검색할 때 AI DB에 없는 곡이면 iTunes를 호출한다. 이때 사용자는 그 곡을 즉시 격자에 등록할 수 있지만, 벡터가 없으므로 당일 추천 후보에는 등장하지 않는다. 해당 곡은 메타데이터만 먼저 적재되고 야간 배치에서 임베딩과 mood 태그를 얻은 뒤 추천 후보로 편입된다.

상태 | 의미 | 추천 후보
-- | -- | --
`embedded` | 벡터와 mood 태그 완비 | 포함
`pending` | 메타데이터만 적재, 배치 대기 | 제외
`no_preview` | 미리듣기가 없어 임베딩 불가 | 영구 제외
`failed` | 다운로드·인코딩 실패, 재시도 대상 | 제외

`track_id`를 기본키로 사용하므로 중복 예약은 자동으로 제거된다. 상태 값과 재시도 횟수는 초기안이며 배치 운영 후 조정한다. 오디오 파일은 임베딩 추출 직후 삭제하고 저장하지 않는다.

### 2.4 구성요소별 도입 이유와 효과

구성요소 | 도입 이유 | 효과와 운영 조건
-- | -- | --
Spring / AI 서버 분리 | 인증·서비스 데이터와 추론 책임을 분리 | 모델·파이프라인 변경이 풀스택 작업을 멈추지 않음. 대신 계약 변경 시 양쪽 합의 필요
FastAPI + Pydantic | 입력·외부 출력·응답 계약을 같은 계층에서 검증 | 잘못된 입력이 모델 호출 비용으로 이어지지 않음
LangGraph 추천 워크플로 | 단계 이름과 실행 경계를 코드로 고정 | 단계별 지연·실패 지점 구분. 단계 계측은 별도 구현이 필요

검색 문장 재구성 단계 | 요청 문장 그대로는 지시·말투가 섞이고 장면 서술은 신호가 약함 | 상황·분위기 중심의 한국어 문장으로 검색. 변환 품질이 추천 품질을 직접 좌우하는 단일 지점이 됨
안내 생성 | 텍스트는 선정 곡 기반 종합 안내, 사진은 VLM 설명 | 곡별 이유 호출 제거. 안내 품질 비교는 별도 검증 필요
AI PostgreSQL 원본 / Spring MySQL 서비스 데이터 | 수집·검색 책임과 사용자 트랜잭션 책임 분리 | 교차 쓰기 방지. 최근 추천·격자 저장 정보는 계약으로 전달해야 함
야간 수집·임베딩 배치 | 온라인 경로에서 오디오 처리를 제거 | 서빙에 오디오 런타임 불필요. 신곡은 최대 1일 지연 후 추천 가능
Provider Adapter | LLM·STT·VLM·날씨·장소·음악 공급자를 인터페이스 뒤에 격리 | 공급자 교체가 REST 계약에 영향을 주지 않음. 부하 테스트 Mock도 같은 구조로 해결
프로세스 메모리 상태를 사용하는 AI 서버 | 대화·요청 제어를 현재 프로세스에서 관리 | 다중 워커·수평 확장 전에 상태 공유와 요청 제어 수정 필요
REST + Adapter (MCP 미도입) | 고정된 소수 도구를 한 서버가 호출하는 현재 범위 | 추가 서버·권한 관리 없음. 도구 재사용 요구가 생기면 재검토

## 3. 전체 요청 흐름

```mermaid
flowchart TB
    INPUT{입력 유형}

    INPUT -->|텍스트| TEXT[메시지 검증]
    INPUT -->|음성| VOICE[오디오 검증 · STT]
    VOICE --> CONFIRM[사용자 전사문 확인 · 전송]
    CONFIRM --> TEXT

    INPUT -->|사진| IMAGE[이미지 검증 · VLM 적합성 판정]
    INPUT -->|위치| LOC[좌표 검증 · 날씨 · 장소 조회]

    IMAGE -->|부적합| REJECT[재촬영 안내]
    LOC -->|모든 소스 실패| ERR[503 LOCATION_CONTEXT_UNAVAILABLE]

    TEXT --> SD[검색 문장 생성 · LLM]
    IMAGE -->|적합 · VLM 검색 문장| EMB
    LOC -->|컨텍스트 확보| SD

    SD --> EMB[Gemini 임베딩]
    EMB --> SEARCH[최근 추천 ID 제외 · pgvector 후보 검색]
    SEARCH --> RERANK[동일 아티스트·제목 중복 제거]
    RERANK --> EMPTY{후보가 있는가}
    EMPTY -->|없음| NONE[200 tracks 없음 안내 메시지]
    EMPTY -->|있음| KIND{입력 유형}
    KIND -->|텍스트| ANSWER[종합 안내 LLM]
    ANSWER --> VALID[곡 응답 구성]
    KIND -->|사진 · 설명은 이미 전송| VALID
    VALID --> RESULT[SSE 추천 결과 반환]
```

입력 처리 방식은 다르지만 검색 문장 이후의 검색·중복 제거·응답 검증은 공통 모듈을 사용한다.

## 5. 주요 설계 결정

### 5.1 모델이 곡을 생성하지 않는다

추천 결과는 AI PostgreSQL에 실재하는 곡에서만 나온다. LLM이 곡명을 생성하는 방식은 존재하지 않는 곡을 반환할 수 있고 이를 걸러낼 검증 계층이 별도로 필요하지만, 벡터 검색은 DB의 `track_id`만 반환하므로 그 계층 자체가 불필요하다. 유효 곡 비율과 미리듣기 제공률은 품질 지표가 아니라 회귀 감시 지표가 된다.

### 5.2 소리 서술 변환을 별도 단계로 둔다

설계 단계의 CLAP 텍스트 인코더는 영어 전용이었고, 장면을 그대로 서술한 질의는 파일럿에서 노이즈 수준의 유사도를 보였다. 그래서 모든 입력을 "어떤 장면인가"가 아니라 "어떤 음악이 어울리는가"를 서술한 문장으로 변환해 검색하는 원칙을 세웠다. 현재 구현은 다국어를 지원하는 Gemini 임베딩으로 전환해 이 문장을 한국어로 만든다. 텍스트는 `recommend_query`, 사진은 `music_query`가 검색 입력이며, 사용자에게 노출되는 추천 이유와 안내 문장은 별도로 생성한다.

### 5.3 추천 이유는 확정된 곡의 태그로 생성한다

텍스트·사진 모두 곡별 이유 LLM을 제거했다. 텍스트 종합 안내는 검색 후 생성하고, 사진 설명은 VLM 분석 결과를 검색 전에 전송한다.

검색이 끝난 뒤, 선정된 곡의 mood 태그와 메타데이터를 LLM 입력에 추가해 설명을 만든다. 검색 결과로 모델 입력을 보강하는 구조이므로 RAG에 해당하지만, LLM은 후보 집합 밖의 곡을 언급할 수 없도록 제약한다. mood 태그는 배치에서 미리 추출해 저장하므로 서빙 시점에 오디오를 다시 받지 않는다.

### 5.4 음성 입력은 사용자 확인을 거친다

STT 결과를 바로 추천에 사용하지 않는다. 전사문을 채팅 입력창에 초안으로 표시하고, 사용자가 수정·확정한 텍스트만 추천 요청으로 전달한다. 인식 오류가 잘못된 추천으로 직접 이어지지 않도록 하기 위한 경계다.

### 5.5 사진은 제출 화면에서 판정한다

이미지 형식·크기·손상 여부를 확인하고, 한 번의 VLM 호출로 추천 적합성 판정, 한국어 검색 문장과 사진 설명 생성을 함께 수행한다. 판정은 SSE의 첫 결과로 먼저 전달되므로 부적합한 사진은 검색 단계로 넘어가지 않는다. 검색 문장이 만들어진 이후 검색 결과가 없는 경우는 장애가 아니므로 빈 `tracks` 이벤트로 반환한다. 기술적으로 처리할 수 없는 이미지와 추천에 적합하지 않은 사진, 결과가 없는 경우를 각각 다른 응답으로 구분한다.

### 5.6 외부 공급자를 분리한다

현재는 기능별 모델 호출 함수와 OpenRouter 설정 모듈을 사용한다. 공통 Provider Adapter 클래스 계층과 부하 테스트 Mock 모드는 설계안이다. 사진 VLM은 같은 Scene 스키마로 외부 API와 선택적 자체 폴백을 연결한다. 폴백은 임베딩 단계까지 대체하지 않는다.

### 5.7 점진적으로 확장한다

초기에는 Docker 기반의 단일 컨테이너로 시작한다. 확장 판단 기준은 CPU 사용률이 아니라 동시 처리 요청 수와 엔드포인트별 p95이며, 실제 한계는 인스턴스보다 요청당 모델 호출 비용에서 먼저 온다고 본다.

## 7. 현재 아키텍처의 강점과 약점

### 강점

- 곡 카드는 DB에서 검색한 곡만 반환한다. 생성 문장의 사실성과 저장된 링크의 유효성은 별도 검증 대상이다.
- 입력 방식이 늘어도 경로가 하나로 유지된다. 텍스트·음성·사진은 검색 문장을 만드는 앞단을 거쳐 검색·중복 제거 모듈을 공유한다. 위치 입력은 이 경로를 재사용하도록 설계한다.
- 추천마다 iTunes를 호출하지 않으므로 외부 음악 API의 지연과 호출 한도가 추천 응답 시간에 직접 영향을 주지 않는다.
- 품질 문제를 "검색이 잘못 골랐는가"와 "설명이 어색한가"로 분리해 관측할 수 있다. 원인 구간이 섞이지 않는다.
- 원본 오디오 대신 메타데이터·벡터·태그를 저장한다. 현재 Gemini 벡터는 3072차원이며, DB·인덱스 저장량은 별도 측정해야 한다.
- 사진 VLM 호출은 외부·자체 서버에 같은 입력·출력 계약을 사용한다. 공급자별 구조화 출력 호환성은 검증이 필요하다.
- 기능별 모듈이 분리되어 있으나, 확장 시에는 대화 상태와 사진 요청 제어의 공유가 필요하다.

### 약점과 위험

- 코퍼스에 없는 곡은 추천할 수 없다. 추천 품질의 상한이 코퍼스 구성에 직접 묶여 있으며, 문서 작성 시점 현재 규모는 약 15,000곡이다.
- 소리 서술 변환이 단일 실패 지점이다. 이 프롬프트의 품질이 추천 품질을 직접 좌우하는데, 검증은 수작업 문장으로만 이루어졌고 LLM 생성 문장으로는 아직 재현되지 않았다.
- 사용자 유입 곡의 자동 적재·야간 처리는 설계안이다. 현재 추천은 Gemini 임베딩과 스토어 링크가 있는 곡만 대상으로 하며 `preview_url`은 null일 수 있다.
- 야간 배치를 운영하려면 실패 알림·재처리 경로와 완료 기준이 필요하다.
- 향후 등록용 iTunes 검색과 배치를 운영하면 호출 한도를 함께 관리해야 한다. 현재 AI 온라인 추천·곡 조회에는 iTunes 호출이 없다.
- 미리듣기 음원의 분석·파생 데이터 보관에 대한 이용 조건이 아직 확인되지 않았다. 단계 5의 수집·삭제 기록은 실험 수행 사실이지 이용 허가가 아니다.
- 사용자 행동으로 추천 품질을 확인할 수 없다. 좋아요·싫어요를 수집하지 않으므로 품질 평가가 전적으로 고정 평가 세트와 내부 블라인드 평가에 의존한다.
- 처리 용량은 부하 시험 전이다. 사진은 프로세스당 2건·동일 채팅 1건으로 제한되며, 대화·중복 기록은 다중 워커에 공유되지 않는다.

## 8. 프로젝트 회고

아래 실험과 변경 결정은 초기 CLAP 설계 주차 기록이다. 현재 온라인 검색은 Gemini 임베딩을 사용한다.

### 8.1 배운 점

**"좋은 모델"보다 "무엇을 검색하는가"가 먼저였다.** 초기에는 추천 품질을 LLM 성능 문제로 보고 프롬프트와 모델 크기를 조정할 계획이었다. 그러나 파일럿에서 품질을 실제로 가른 것은 코퍼스 구성이었다. 키워드 검색으로 수집한 대량 유통 배경음악이 임베딩 공간 중앙에 자리 잡고 모든 애매한 질의를 흡수했다. 수집 방식을 아티스트 식별자 기반으로 바꾸자 이 현상이 사라졌다. 모델을 건드리지 않고 데이터만 바꿔서 얻은 개선이다.

**질의의 언어와 서술 방식이 검색 성능을 지배했다.** 같은 상황을 장면으로 서술했을 때와 소리로 서술했을 때 유사도가 최대 3배 차이 났다. 더 극단적으로, 의미가 정반대인 한국어 문장 두 개의 유사도가 0.912였다. 모델이 한국어를 부정확하게 처리하는 것이 아니라 모든 한국어 입력을 사실상 같은 좌표로 축약한다는 뜻이었다. 사용자 언어와 검색 질의 언어를 분리해야 한다는 결론은 이 측정에서 나왔다.

**할루시네이션은 막는 것보다 발생할 자리를 없애는 편이 쌌다.** 처음에는 LLM이 생성한 곡을 iTunes로 검증하는 구조였다. 검증 계층, 재시도 정책, 매칭 실패 시 후보 보충까지 필요했다. 검색이 곡을 선정하는 구조로 바꾸자 이 계층이 통째로 사라졌다. 문제를 잘 처리하는 것과 문제가 생기지 않는 구조를 만드는 것은 다른 일이었다.

**측정이 설계를 실제로 되돌렸다.** 태그 기반 비교, 키워드 기반 수집, LLM 곡 생성은 모두 문서에 적혀 있던 계획이었고 실측 후 폐기했다. "측정 후 판단한다"는 원칙은 도입을 미루기 위한 표현이 아니라, 이미 내린 결정을 뒤집는 데도 적용되어야 의미가 있다는 것을 확인했다.

**외부 API의 문서와 실제 동작은 달랐다.** KR 스토어 조회가 0건이고, `offset`이 동작하지 않으며, `artistTerm`이 퍼지 매칭으로 LISA를 다른 아티스트에 연결하는 것은 모두 직접 호출해 보고서야 알았다. 외부 의존성은 조사 단계에서 끝내지 말고 최소 호출이라도 실행해 확인해야 한다.

## 10. 최종 결론

머문음의 AI 서빙 구조는 하나의 원칙으로 설명된다. 지금 근거로 확인된 것만 구조에 고정하고, 확인되지 않은 것은 교체 가능한 자리에 둔다.

첫째, 책임 경계가 계약으로 고정되어 있다. 모바일은 AI 서버를 직접 호출하지 않고, 인증과 서비스 데이터는 Spring이, 입력 검증과 추천 생성은 AI 서버가 맡는다. 두 파트는 REST 계약만 공유하므로 AI 내부의 모델과 파이프라인이 바뀌어도 풀스택 쪽 작업이 멈추지 않는다.

둘째, 입력 방식이 늘어도 경로는 하나로 유지된다. 텍스트, 음성, 사진, 위치는 소리 서술을 만드는 앞단만 다르고 검색과 응답 정제는 같은 모듈을 쓴다. V2는 공통 곡 객체를 재사용하지만 판정·장면·거절 SSE 처리를 FE에 추가해야 한다. V3의 실제 연동은 아직 구현하지 않았다.

셋째, 곡은 모델이 만들어내지 않는다. 사용자에게 반환되는 곡은 코퍼스에 실재하는 곡뿐이고, 모델은 검색 이전의 질의 변환과 검색 이후의 설명만 담당한다. 존재하지 않는 곡이 노출되는 실패 모드가 구조적으로 차단되며, 품질 문제를 검색 문제와 설명 문제로 나누어 볼 수 있다.

넷째, 도입 판단 기준이 모든 단계에서 동일하다. 오픈웨이트 자체 서빙, 협업 필터링, Kubernetes, MCP, 마이크로서비스 분리는 모두 보류하거나 조건부로 두었고, 조건은 예외 없이 현재 구조의 실패가 측정으로 확인되었을 때다. 이 원칙은 선언에 그치지 않았다. 태그 기반 비교, 키워드 기반 수집, LLM 곡 생성은 모두 문서에 적혀 있던 계획이었고 실측 후 폐기했다. 측정이 설계를 실제로 되돌린 이력이 있다는 점이 이 구조를 신뢰할 근거다.

다섯째, 확장 시점의 판단 근거를 미리 확보했다. 현재 AI 서버의 대화·사진 요청 제어는 메모리 상태에 의존하므로 수평 확장 전에 상태 공유를 구현해야 하며, 확장 트리거는 CPU 사용률이 아니라 동시 처리 요청 수와 p95로 정의했다. 동시에 실제 한계가 인스턴스가 아니라 요청당 모델 호출 비용에서 먼저 온다는 점도 명시했다.

이 아키텍처를 V1·V2 개발과 풀스택 연동의 기준으로 사용한다. API 변경 시 요청·응답·SSE 계약을 함께 갱신하고, 배포 검증은 검색 품질·응답 지연·비용·동시 처리 기준에 따라 수행한다.
