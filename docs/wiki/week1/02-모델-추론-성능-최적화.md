# 모델 추론 성능 최적화

## 설계 목표

머문음은 사용자의 텍스트,음성, 이미지, 또는 특정 위치 GPS 입력을 받아 상황에 어울리는 음악을 추천한다.  
  
MVP에서는 외부 LLM API와 STT API를 활용해 기능을 안정적으로 완성하고,  
최초 통합 버전의 성능을 기준선으로 측정한다.  
이후 실제 병목을 개선하고, 오픈웨이트 모델과 GPU 환경은  
비용 및 운영 가능성을 판단하기 위한 비교 실험으로 진행한다.  

```text
텍스트/이미지/GPS좌표 입력  
→ Spring
→ FastAPI
→ LLM API
→ iTunes 검색
→ 추천 결과 반환

음성 입력
→ Spring
→ FastAPI
→ STT API
→ 전사문 반환
→ 사용자 확인·수정
→ 텍스트 메시지 전송
```

## 1. 기존 모델 추론의 성능 지표

### 기준선 정의

본 문서에서 기존 성능은 외부 모델의 공개 벤치마크가 아니라,  
외부 LLM·STT API를 연결한 MVP 최초 통합 버전의 실측 결과를 의미한다. 

실제 서비스와 동일한 요청 흐름에서 다음 항목을 측정한다.

| 구간 | 측정 지표 | 측정 시점 |
|---|---|---|
| 음악 추천 | 전체 응답 시간 p50·p95 | MVP 최초 통합 후 |
| LLM | API 호출 시간, 입력·출력 토큰 수 | MVP 최초 통합 후 |
| 음악 검색 | iTunes 검색 및 후처리 시간 | MVP 최초 통합 후 |
| 음성 입력 | STT 전체 응답 시간 p50·p95 | MVP 최초 통합 후 |
| 음성 전처리 | Base64 디코딩 및 FFmpeg 처리 시간 | MVP 최초 통합 후 |
| 응답 안정성 | JSON 형식 준수율, 오류율 | MVP 최초 통합 후 |
| 추천 품질 | 검색 가능한 곡 비율, 추천 적합도 | MVP 최초 통합 후 |
| 비용 | 요청 100건당 LLM·STT 비용 | MVP 최초 통합 후 |

### 측정 조건

- 음악 추천 결과는 기본 3곡, 최대 5곡으로 고정한다.
- 동일한 한국어 입력 세트를 최적화 전후에 사용한다.
- STT는 5초·15초·30초 음성으로 구분한다.
- 평균값뿐 아니라 p50과 p95를 함께 기록한다.
- 각 요청은 LLM, STT, iTunes, 전처리 구간으로 나누어 측정한다.
- 추천 속도와 추천 품질을 함께 평가한다.
- 자체 모델 실험은 cold start와 warm 상태를 구분한다.

### 품질 평가 기준

| 평가 항목 | 확인 내용 |
|---|---|
| 한국어 자연스러움 | 추천 이유가 문맥에 맞고 어색하지 않은가 |
| 상황 적합성 | 사용자의 시간·장소·감정과 추천곡이 어울리는가 |
| 음악 검색 성공률 | 추천된 곡을 iTunes에서 실제로 찾을 수 있는가 |
| 응답 형식 | 정해진 JSON 필드와 타입(Hard) 그리고 규칙(Soft)을 지키는가 |

추가적으로 v2에서 태그 방식의 중간 결과를 도출할 시, 다음과 같은 평가 항목을 넣을 수 있다

평가 항목 | 확인 내용 | 평가 지표
-- | -- | --
LLM이 인식하기 힘든 상황 반영 | 인식이 혼동될 수 있는 데이터셋을 잘 판별하는가 | "distractor" 필드 활성 데이터셋 정답률
필드별 적합성 | 사진에서 성질 별로 의도된 분위기를 파악할 수 있는가 | 태그 필드 별 임계값 기준 F1

## 2. 성능 병목 요소와 원인

초기에는 다음 항목을 예상 병목으로 설정하고, 구간별 측정을 통해 실제 영향도를 확인한다.

| 우선순위 | 예상 병목 | 원인과 영향 |
|---|---|---|
| 높음 | LLM 응답 지연 | 외부 API 네트워크, 모델 추론 시간, 출력 토큰 수에 따라 전체 응답 시간이 달라진다. |
| 높음 | iTunes 다중 검색 | 추천곡을 제목별로 조회하면 여러 번의 외부 API 호출이 누적될 수 있다. |
| 높음 | 잘못된 응답 형식 | 필수 필드가 누락되거나 JSON 형식이 맞지 않으면 재요청과 후처리가 필요하다. |
| 중간 | 불필요하게 긴 프롬프트 | 짧은 음악 추천 요청에 과도한 대화 이력이나 문서를 포함하면 입력 토큰과 지연이 증가한다. |
| 중간 | STT 전처리 | Base64 디코딩, 파일 검증, FFmpeg 변환 과정이 추가된다. |
| 중간 | 외부 API 편차 | LLM·STT·iTunes 제공자의 네트워크 상태에 따라 p95 응답 시간이 증가할 수 있다. |
| 조건부 | RAG 검색 | 모든 요청에 검색을 적용하면 단순한 추천에도 검색 지연과 비용이 추가된다. |
| 실험 단계 | 자체 모델 cold start | 서버리스 GPU가 0대에서 시작하면 모델 다운로드와 로딩 시간이 발생한다. |
| 실험 단계 | GPU 메모리 부족 | 모델 가중치, KV Cache, 동시 요청이 GPU 메모리를 함께 사용한다. |

전체 응답이 느리다는 이유만으로 모델 자체를 병목으로 판단하지 않는다.  
LLM 추론, 네트워크, 음악 검색, 전처리 시간을 분리하여 가장 큰 구간부터 개선한다.  

### 품질 저하

우선순위 | 품질 저하 요인 | 원인과 영향
-- | -- | --
높음 | 존재하지 않는 곡 생성 | LLM이 내재 지식만으로 곡을 만들어 iTunes에 없는 제목을 반환한다. 3곡 중 일부가 누락되어 추천 수가 줄고, 유저는 서비스가 부실하다고 느낀다.
높음 | 잘못된 응답 형식 | 필수 필드 누락이나 JSON 파싱 실패로 추천이 나가지 못한다. 유저는 원인을 알 수 없고 "가끔 안 되는 서비스"로 인식해 재시도하지 않는다.
중간 | 추천 다양성 부족 | LLM이 인기곡으로 쏠려 서로 다른 상황에도 비슷한 곡을 반환한다. 유저는 아는 곡이 몇 개 없는 서비스로 느끼고 재방문 동기가 줄어든다.
중간 | 유사 입력 간 결과 편차 | 비슷한 문장인데 추천이 크게 달라진다. 유저는 추천에 근거가 없다고 느껴 신뢰하지 않는다.
중간 | 상황 해석 실패 | 은유적이거나 모호한 표현("무기력하다", "이사 온 첫날")에서 상황을 잘못 읽는다. 추천 이유는 그럴듯한데 곡이 안 맞아, 유저는 자기 말을 못 알아들었다고 느낀다.
조건부 | 최신 곡 부재 | 모델 학습 시점 이후 발매곡을 추천하지 못한다. 최신 곡을 기대하는 유저에게는 서비스가 뒤처져 보인다.

## 3. 적용할 최적화 기법의 구체적 계획

### 3-1. 최적화 기법

각 기법은 서비스적 가정 → 사용하는 자원 → 자원 분석 → 평가 지표 → 비고 순으로 정리했다.  
자원 분석 항목이 길 경우, 따로 분리해서 보여준다.

절 | 기법 | 버전 | 사용하는 자원
-- | -- | -- | --
3-1-1 | 출력 토큰 절감 | 공통 | 출력 토큰
3-1-1 | 프롬프트 품질 개선 | 공통 | 입력 토큰
3-1-2 | 검증 재시도 | 공통 | LLM 호출 · GPU 시간
3-1-2 | 부분 재시도 | 공통 | LLM 호출 · 응답 시간
3-1-2 | Self-Consistency | 공통 | LLM 호출 · GPU 시간
3-1-3 | 모델의 크기 | 공통 | 요청당 비용 · VRAM

3-1-5 | 이미지 해상도 상향 | v2 | 이미지 토큰 · GPU 시간 · VRAM


### 3-1-1. (공통) 프롬프트 개선

### ㄱ. 출력 토큰 절감

| 구분 | 내용 |
|:--|:--|
| **서비스적 가정** | 사용자는 추천 이유를 읽으러 오는 게 아니라 곡을 들으려고 온다.<br>이유가 길면 오히려 스크롤이 생기고 곡 카드가 밀린다.<br>짧은 한 문장이 긴 설명보다 비용도 아끼고 UX상 더 나을 수 있다. |
| **사용하는 자원** | `출력 토큰` |
| **자원 분석** | LLM 응답 시간은 출력 토큰 수에 거의 비례함.<br>reason이 3곡, 곡당 200자, 한국어 기준 300\~400토큰,<br>60자로 줄이면 150토큰 안팎.<br>비용은 출력 토큰이 입력의 5배 단가로 절감폭이 큼. |
| **성능 평가 지표** | 길이별 추천 적합도 점수를 보고, 줄일 수 있는 글자수를 계산한다. |

<br>

### ㄴ. 프롬프트 개선: 품질 개선

| 구분 | 내용 |
|:--|:--|
| **서비스적 가정** | 사용자는 채팅을 올리면서 자신의 의도와 맞지 않는 음악이 추천되면 서비스가 자신의 말을 제대로 이해하지 못 한다고 느낀다. 사용자의 말을 왜곡 없이 이해할 수 있어야 한다<br>`(v2)` 사진을 올리면서 바다 사진을 올렸는데 실내 카페 음악이 나오면, 서비스가 자기 사진을 제대로 안 봤다고 느낀다. 사용자가 주인공이라고 생각한 대상이 중간 태그에 반드시 들어가야 한다. |
| **사용하는 자원** | `입력 토큰` |
| **자원 분석** | 입력 토큰이 소모되나,<br>시스템 프롬프트는 전 요청 공통이여서 크게 자원 제약을 신경 쓸 수 없음 |
| **품질 평가 지표** | `distractor` 필드.<br>프롬프트는 어느 정도 확신한 정답을 바꾸는 데는 한계가 있다.<br>대신 규칙을 추가함으로써 함정 문제를 회피할 수 있다. |

> [!NOTE]
> **비고** — **Prefix Caching**으로 사실상 자원 제약 없음.
> 다만 자원이 남는다고 무조건 길게 쓰는 것도 좋지 않다.
> 지시가 길어질수록 모델이 일부 규칙을 무시하는 경향이 나타나고,
> 예시를 추가하면 그 예시 쪽으로 판단이 편향된다.

### 3-1-2. (공통) 재시도 정책

### ㄱ. 검증 재시도

| 구분 | 내용 |
|:--|:--|
| **서비스적 가정** | 사용자는 실패를 이해하지 못한다. 명세한 대로 추천이 안 나오면 "이 서비스는 가끔 안 된다"로 인식하고 다시 시도하지 않는다. 품질 이전에 응답이 항상 나와야 한다. |
| **사용하는 자원** | `LLM 호출 횟수와 비용` `(v2) GPU 시간` |
| **자원 분석** | 재시도율만큼 LLM 호출이나 GPU 시간으로 인한 평균 비용 상승<br>소수 요청 두 배라 크게 제약이 되진 않음 |
| **품질 평가 지표** | JSON 파싱 성공율, `(v2)` F1 |

> [!NOTE]
> **비고** — 재시도로 인해 p99는 두 배가 될 수 있다
> **Constrained Decoding**을 쓰면 재시도율이 줄어들 것으로 예상된다
> (이 또한 사실 품질 개선이다. 대신 실패율이 적은 보장된 품질 개선이다)
> 재시도 상한을 둬서 시간을 줄일 수 있을 것이다
> `(v2)` Vision Embedding을 **Caching**해서 재시도 시 ViT 재실행 회피

<br>

### ㄴ. 부분 재시도

| 구분 | 내용 |
|:--|:--|
| **서비스적 가정** | 3곡 중 1곡만 문제가 있을 때 전체를 다시 부르면 정상이던 2곡의 추천 이유까지 바뀐다. 사용자가 같은 요청을 두 번 했을 때 결과가 통째로 달라지고, 사용자를 두 배 기다리게 하여 신뢰가 떨어진다. |
| **사용하는 자원** | `LLM 호출 횟수` `응답 시간` |
| **자원 분석** | 재시도율만큼 평균 비용이 오르고 p99가 두 배가 될 수 있음. 상한을 둬서 제어 |
| **품질 평가 지표** | 재시도 발생 시 p99 지연, 최종 응답 성공률 |

<br>

### ㄷ. Self-Consistency

| 구분 | 내용 |
|:--|:--|
| **서비스적 가정** | 모호한 사진에서 모델의 판단이 실행할 때마다 달라진다. 같은 사진을 다시 올렸는데 다른 곡이 나오면 유저는 서비스가 대충 답한다고 느낀다. |
| **사용하는 자원** | `LLM 호출 횟수와 비용` `(v2) GPU 시간` |
| **품질 평가 지표** | iTunes 성공률, JSON 준수율, 적합도 점수, 다양성 점수, `(v2)` N에 따른 F1 개선폭. 포화 지점 탐색 |

**자원 분석**

처리량이 1/N이 됨에 따라 호출 횟수 N배, 혹은 감당 가능 트래픽 1/N
재시도와 다르게 모든 요청이 N배.

self-consistency 또한 해상도 상향과 같이
요청당 KV Cache 소요량을 늘리므로
동시에 적용 시 동시 처리 가능 요청 수 곱으로 감소
피크 시간대 트래픽 고려

> [!NOTE]
> **비고**
> - **Early Stopping**: 같은 답이 나오면 즉시 종료
> - **Batching** 방식 역시 self-consistency에 있어 속도를 개선시키나, early stopping과 같이 이용하기 힘들 수 있음. 그러나 **Continuous Batching**이라면 사용 가능할 수 있다.
> - **Difficulty Routing**: 사진의 복잡도를 판단해 N을 다르게 배정. 시간대 별로 다르게 지정할 수도 있다. 해상도 상향과의 KV cache 증가량 유의미하게 감축 가능

### 3-1-3. (공통) 모델의 크기

| 구분 | 내용 |
|:--|:--|

### 3-1-5. (v2) 이미지 해상도 상향

| 구분 | 내용 |
|:--|:--|
| **서비스적 가정** | 유저는 추천 근거가 될 요소를 화면 중앙에 크게 배치해서 찍지 않는다. 창밖 노을, 멀리 보이는 수평선처럼 화면의 일부만 차지하는 요소가 정작 그 순간의 분위기를 결정하는 경우가 많다. 해상도가 낮으면 이런 요소가 리사이즈 과정에서 소실되어, 모델이 화면의 대부분을 차지하는 배경만 보고 판단하게 된다. |
| **사용하는 자원** | `사진에서 데이터 추출에 사용되는 토큰` `GPU 시간` `VRAM` |
| **품질 평가 지표** | 해상도 당 필드별 임계값 기준 F1<br>포화 지점에서 해상도 상승을 멈출 수 있다.<br>큰 물체가 아닌 세부적인 물체 대상의 사진으로 판단 |

**자원 제약**

VRAM 여유: 총 24GB, 해상도 1280² 가정

| 구성 | VRAM 여유 | 동시 처리 |
|:--|:--|:--|
| 7B-4bit | 17GB | 동시 수십 건 |
| 7B-bf16 | 4GB | 동시 10건 수준의 상한 |
| 32B-4bit ~ | 2GB | 서비스 배치가 불가능 |

피크 시점의 동시 업로드 횟수 파악

\+ 또한 해상도를 올리면 vision token이 많아져,
KV cache도 늘어난 토큰 수에 비례하여,
VRAM의 공간이 더 줄어듦

해상도마다 요청당 GPU 점유 시간 존재
해상도를 올려 처리 시간이 0.4초가 된다면
GPU 한 대당 21만 건까지 가능.
사용가능 GPU는 한 대이므로 특정 시간대 트래픽을 예상해서 해상도를 조절

> [!NOTE]
> **비고** — **Flash Attention**으로 하드웨어 수준에서 F1 손실 없이
> VRAM 사용량 감소 가능 (이미 적용되어 있을 수도 있다)
> 사진이라는 점을 이용해서 기존의 O(N²)을 벗어나
> **Window Attention**도 시도 가능

> [!IMPORTANT]
> 기획 특성 상 저화질 업로드가 고정된다면 해당 최적화는 고려하지 않는다


### 3.2 오픈웨이트 모델 실험

오픈웨이트 모델 실험의 목적은 MVP 모델을 바로 교체하는 것이 아니다. 제한된 예산 안에서 자체 모델을 운영할 때 필요한 GPU 자원, 응답 시간, 비용을 직접 검증하는 데 목적이 있다.

| 후보 | 실험 목적 |
|---|---|
| `Qwen3-8B-AWQ` | 8B급 양자화 모델의 VRAM, 응답 시간, 한국어 추천 품질 측정 |
| `EXAONE-3.5-7.8B-Instruct` | 한국어 생성 품질 비교 |
| 외부 LLM API | 품질·응답 시간·비용의 기준선 |

동일한 음악 추천 평가셋으로 다음 항목을 비교한다.

- 한국어 추천 품질
- iTunes 검색 성공률
- JSON 형식 준수율
- 첫 토큰 생성 시간
- 전체 응답 시간
- GPU 메모리 사용량
- 동시 요청 처리량
- 요청당 비용

### 3.3 GPU 플랫폼 실험

| 용도 | 플랫폼 | 선정 이유 |
|---|---|---|
| 모델 비교·양자화 실험 | RunPod Pod | PyTorch, JupyterLab, SSH 기반 실험 환경을 빠르게 구성할 수 있다. |
| 저비용 공개 데모 | Modal 또는 RunPod Serverless | 유휴 시간에 0대로 축소할 수 있어 초기 고정비를 줄일 수 있다. |
| 운영 환경 후보 | AWS EC2 GPU | 기존 백엔드 인프라와 통합하고 배포·모니터링 경험을 확보할 수 있다. |

실험 순서는 다음과 같다.

```text
외부 API 기반 MVP 완성
→ RunPod에서 오픈웨이트 모델 성능 측정
→ 서버리스 GPU의 cold start와 비용 측정
→ 외부 API와 자체 서빙 비교
→ 서비스에 유리한 경우에만 전환 검토
```

자체 모델을 서빙할 경우 FastAPI 프로세스에 모델을 직접 적재하지 않는다. 별도의 vLLM 추론 서버를 두어 FastAPI worker마다 GPU 모델이 중복 적재되는 문제를 방지한다.
