## 이미 정해진 것

| 항목 | 내용 |
| --- | --- |
| 입력 | 사진 1장. 질문 입력 없음 |
| 화면 | 부적합이면 같은 화면에 바텀시트, 적합이면 추천으로 이동 |
| 범위 밖 | 위치·날씨 API(V3), 기록 기능의 AI |
| 예산 | AI 파트 월 12만 원 (LLM API + GPU 합산) |
| 모델 경로 | OpenRouter가 주 경로, 오픈웨이트 자체 서빙은 폴백 실험 |

## 1. 제품 구조 (가장 먼저 정할 것)

| 안 | 장점 | 단점 |
| --- | --- | --- |
| A. 챗봇 안의 사진 버튼 (현재 설계) | 후속 대화로 이어갈 수 있음 | `thread_id`·대화 메모리·동시성 처리가 복잡함 |
| B. 별도 메뉴, 무상태 | V3 위치 추천과 같은 구조, API가 단순함, 기록 기능과 연결하기 쉬움 | 후속 대화 없음 |
| **제안: B + "이 분위기로 채팅 이어가기"** | 두 안의 장점을 모두 가짐 | 채팅 시작용 계약이 추가로 필요함 |

## 2. FE·BE 계약

| 결정 | 제안 | 이유 |
| --- | --- | --- |
| 판정 전달 | 한 요청 안의 SSE로 `verdict`를 먼저 보냄 | 화면은 판정 결과만 기다리면 됨. V1 SSE 중계를 재사용 |
| 전송 | multipart, 별도 저장소 없음 | 원본을 보관할 필요가 없음. 축소 후 약 300KB라 Base64도 가능 |
| 축소·EXIF | FE: 긴 변 1280px JPEG로 다시 인코딩. AI: 다시 검증 | 업로드와 메모리가 줄어듦. HEIC는 브라우저가 디코딩할 수 있는 경우에만 지원 |
| 결과 구분 | 파일 오류 4xx / 부적합 `verdict` / 곡 없음 `tracks: []` / 장애 `error.reason` | `tracks: []`만으로는 부적합과 곡 없음을 구분할 수 없음 |
| 중복·재시도 | 1차 차단은 BE가 `request_id`로. 같은 ID 재시도는 분석 결과 전 실패만 허용 | 실패 단계마다 과금·상태 변경 여부가 다름 |

## 3. 정책

| 결정 | 제안 |
| --- | --- |
| 판정 기준 | 관대하게. 빈 화면·식별 불가·공급자 차단만 거절 |
| 사진 속 글자 | 장면이 주 근거, 글자는 보조 맥락. 메모에 적힌 내용을 실제 상황으로 보지 않음. **글자만 있는 사진의 허용 여부는 미정** |
| 거절 문구 | 바텀시트 1종을 재사용하고, 사유별로 제목·설명만 바꿈 |
| 피드백 | 카드에 좋아요/싫어요. BE가 저장하고, AI는 `request_id`별 추천 기록을 남김. 사용자가 적은 동안은 평가셋 수집과 싫어요 곡 제외에만 사용 |

## 4. AI 내부

| 결정 | 제안 | 이유 |
| --- | --- | --- |
| 주 모델 | OpenRouter 모델 2~3종을 평가셋으로 비교 | 지금은 수동 테스트 결과뿐 |
| 폴백 | 자체 VLM(qwen3-vl 4B/8B)은 VLM 단계만 대체 | 임베딩은 Gemini로 고정 |
| GPU | 0대 축소를 기본으로, 시연 시간에만 미리 켜 둠. 플랫폼은 wiki에 Modal(06)과 RunPod(08)이 섞여 있어 확인 필요 | 월 예산과 콜드 스타트 |
| 곡별 이유 LLM | 텍스트·사진 공통의 별도 이슈로 제거 검토 | 응답 지연이 늘고, VLM 설명과 역할이 겹침 |

## 5. 평가셋

- 실기기 사진 30장: 적합 20장, 부적합 10장
- 측정: 판정 정확도, JSON 준수율, VLM 지연 p50·p95, 요청당 비용, 추천의 체감 적합도
