# 위치 추천 — 팀 논의 제안

2026-10-27 · [01-구현-현황](01-실험-구현-현황.md)을 바탕으로 한 팀 논의 제안. 현재 연동 기준은 [API 설계](../../wiki/week1/01-모델-API-설계.md)의 "5. 위치 음악 추천"이다. 아래는 변경 논의 항목이며 합의 전까지 현재 계약을 대체하지 않는다.

## 기준 자료

- 화면: DISC-001 (자동 표시 조건), MAP-001
- 초기 설계: [API 설계](../../wiki/week1/01-모델-API-설계.md) 5번, [서비스 인프라](../../wiki/week2/07-서비스%20인프라%20확장성과%20모니터링%20설계.md)

## 이미 정해진 것

| 항목 | 내용 |
| --- | --- |
| 경로 | `POST /v1/location/recommendations` (위키 그대로) |
| 입력 | 위도·경도. 채팅·`thread_id` 없음 |
| 결과 | 공통 `track` 객체 최대 5개 |
| 좌표 처리 | 정확한 좌표는 외부 조회에만 쓰고 모델에 넘기지 않음. AI 서버는 좌표를 저장하지 않고 로그에는 소수 둘째 자리(약 1km)만 남김 |
| 호출 경로 | Client → Spring → AI Server. AI 서버는 Docker 내부 8000 포트, 변경 없음 |

## 1. FE·BE 계약

| 결정 | 제안 | 이유 |
| --- | --- | --- |
| `message` | **응답에서 제거** | DISC-001에 문장을 보여줄 자리가 없음. 위키 계약에는 `message`가 있음 |
| 응답 형식 | SSE 대신 JSON 한 번 | 팝업은 곡이 모두 정해진 뒤에 뜨므로 스트리밍할 대상이 없음 |
| `exclude_track_ids` (신규, 선택) | BE가 이미 보여준 곡 ID를 넘김 (최대 100) | 위치 추천은 대화가 없어 AI 서버가 최근 곡을 기억하지 않음. 같은 날 다른 격자에서 같은 곡이 반복될 수 있음 |
| `context` | 응답에 포함, 표시용 참고 정보 | 팝업에 "바다·숲" 아이콘 등을 띄우고 싶을 때. 규칙 개선에 따라 값이 바뀔 수 있어 저장·분기에 쓰지 않는 것을 권장 |
| `music_query`·`query_source` | 디버깅용. FE·BE는 의존하지 않음 | 예고 없이 바뀔 수 있음 |
| 검증 실패 코드 | **422** `INVALID_REQUEST` | 위키 표는 400이지만, 사진·STT와 같은 422로 구현함. 하나로 맞출 필요 |
| 응답 시간 | 5~6초 (외부 조회 0.9초 + 검색어 생성 + 검색) | 팝업은 늦게 떠도 된다는 전제. BE 타임아웃은 15초 이상 권장 |
| `user_context` | 받지 않음 | 위키에는 선택 필드로 있으나 쓸 단계가 없음(사진과 같은 판단) |

## 2. 표시 조건은 FE·BE 담당

DISC-001의 자동 표시 조건(10분 주기, 정확도 300m, 격자 판정, 저장 기록·당일 소비 여부, 미리듣기 중 보류, 30분 쿨다운, 하루 3회, MAP-001에서만 표시)은 **AI 서버가 알 수 없다.** AI 서버는 "추천이 필요하다"고 판단된 좌표만 받는다.

- 격자 단위와 좌표 반올림은 FE·BE가 정한다. AI 서버의 판정 반경은 500m(밀도)~2km(관광명소)라, 격자가 너무 작으면 인접 격자가 거의 같은 결과를 받는다.
- 같은 격자를 다시 요청하면 곡은 매번 새로 검색한다. 결과 재사용(캐시)은 BE가 격자별로 저장하는 쪽이 맞다. 카카오는 결과 저장을 금지하므로 AI 서버는 장소 원본을 캐시하지 않는다.

## 3. 인프라

| 결정 | 제안 | 이유 |
| --- | --- | --- |
| 카카오 키 | 배포 환경변수 `KAKAO_REST_API_KEY` **필수** | 배포 이미지에 OSM이 없으면 카카오 키가 없을 때 모든 요청이 503 |
| 카카오 앱 | 현재 개인 계정 "머문음" 앱을 팀원 추가로 공유 | 무료 쿼터(카테고리 검색 일 10만 건 ≈ 하루 약 1만 회 추천)는 계정에서 처음 활성화한 앱에만 붙음 |
| OSM 배치 | 1차는 OSM 없이 배포(카카오만), 2차에 결정 | 자연 판정 정확도가 크게 다름(정답 세트 22/31 → 31/31) |
| OSM 2차 안 | ① 서버 메모리: 157MB 파일 + `shapely`를 이미지에 포함 ② PostGIS: 기존 DB에 확장 설치 후 지형 테이블(도형 69MB + 인덱스) | ②가 정석이지만 배포 DB 이미지가 PostGIS를 지원하는지 확인 필요 |
| OSM 갱신 | 월 1회 Geofabrik 파일로 재추출 | 지형은 거의 바뀌지 않음 |
| Open-Meteo | 날씨·고도 사용 | 무료 API는 비상업 용도 기준. 상업 서비스가 되면 유료 플랜 확인 |
| Google Places | 사용하지 않음 | 01 문서의 공급자 비교 참고. 키·스크립트는 비교용으로만 남김 |

## 4. AI 내부 (계약과 무관하게 계속 개선)

- 검색어 방식: 실제 `recommend_query` 분포에 맞춘 짧은 문장(고유명사·감성 형용사 제외)을 비교 중
- 밤의 술집거리(`nightlife`), 도심 뒤 산, 오름 등 판정 보완
- 지도 클릭으로 판정 근거를 보는 로컬 실험 페이지

## 5. 위키 수정 제안 (API 설계 5번)

| 현재 위키 | 실제 구현 |
| --- | --- |
| Google Places 반경 500m, 희소하면 2km 재조회 | 카카오 로컬(밀도·이름) + OSM(자연 지형) + 고도 기복(산) |
| LLM이 곡 후보 생성 → iTunes 조회 | LLM은 검색 문장만 생성 → 기존 임베딩·DB 검색 (V1·V2와 같음) |
| 추천 이유 생성 | 없음 |
| 컨텍스트 캐시(선택) | AI 서버는 캐시하지 않음 (카카오 저장 금지). 필요하면 BE가 결과를 격자별로 저장 |
| 성공 응답 `message`, `tracks` | `tracks`, `context` (+ 디버깅 필드) |
| 검증 실패 400 | 422 |

## 6. 합의 후 바뀔 문서
