# 위치 추천 — 구현 현황

2026-10-27 · 브랜치 `feat/v3-location-recommendation`

**좌표 1개 → 카카오·OSM·고도·날씨 동시 조회 → 규칙으로 장소 특징 판정 → 검색어 생성 → 기존 Gemini 임베딩·PostgreSQL 검색 → 최대 5곡.**

## 실행

```sh
uv sync --locked
uv sync --group location-exp   # 선택: OSM 지형 판정까지 쓸 때 (shapely·osmium)
uv run uvicorn backend.main:app --host 127.0.0.1 --port 8012
```

- API 문서·직접 호출: `http://127.0.0.1:8012/docs` → `POST /v1/location/recommendations`
- 실제 카카오·Open-Meteo·LLM·임베딩·DB를 호출한다. 카카오·Open-Meteo는 무료, LLM·임베딩은 기존 텍스트 추천과 같은 비용 구조다.
- OSM 지형 파일은 커밋하지 않는다. 만들려면 아래 "OSM 파일 준비"를 따른다. 없으면 카카오만으로 판정한다.

| `.env` | 용도 |
| --- | --- |
| `KAKAO_REST_API_KEY` | **필수.** 카카오 로컬(장소·행정동). Kakao Developers 앱에서 카카오맵 사용 설정 필요 |
| `LOCATION_OSM_FEATURES` | 선택. OSM 지형 파일 경로. 기본 `out/osm/features.jsonl` |
| `OPENROUTER_LLM_API_KEY`·`LLM_MODEL` | 검색어 생성. V1과 같은 값 |
| 기존 임베딩·DB 설정 | 검색. V1과 같다 |

OSM 파일 준비 (약 1분, 결과 157MB):

```sh
mkdir -p out/osm
curl -L -o out/osm/south-korea-latest.osm.pbf https://download.geofabrik.de/asia/south-korea-latest.osm.pbf   # 약 290MB
uv run --group location-exp python scripts/location/extract_osm.py
```

## 소스별 실패 처리

위키의 "한쪽 컨텍스트만 확보해도 추천을 계속한다"를 따른다.

| 실패 | 처리 |
| --- | --- |
| 카카오 | OSM만으로 자연 판정. 밀도는 moderate, 지역명·특징 없음 |
| OSM (파일·shapely 없음 포함) | 카카오만으로 판정 |
| 카카오 + OSM | **503 `LOCATION_CONTEXT_UNAVAILABLE`** |
| 고도 | 산 판정만 건너뜀 |
| 날씨 | 날씨 없이 진행. 시간대는 한국 평균 일출·일몰로 어림. 없는 날씨를 지어내지 않음 |
| LLM 미설정·공급자 오류·시간 초과 | 503 `MODEL_UNAVAILABLE` (V1과 같음) |
| LLM 응답 형식 오류 | 503 `MODEL_RESPONSE_INVALID` (V2와 같음) |
| 임베딩·DB | 503 `MODEL_UNAVAILABLE`·`MUSIC_CATALOG_UNAVAILABLE` (V1과 같음) |
| 소스 하나가 30초 초과 | 그 소스만 실패로 보고 위 규칙대로 진행 |
| 요청 전체 90초 초과 | 503 `LOCATION_TIMEOUT` |

타임아웃은 V1처럼 단계마다 30초(외부 조회는 동시 호출이라 30초 하나, LLM 30초, 임베딩 30초)를 주고, 요청 전체 상한은 그 합인 90초다. BE는 100~120초 이상을 권장한다.

카카오 실패 시 밀도 가정(moderate), 날씨 실패 시 시간대 어림, 고도 격자(9×9)는 내부 기준으로 검토 중이다. 정답 세트로 보면 카카오 실패 시 busy로 가정해야 자연 판정이 정상과 같다(31/31, moderate는 27/31).

## API

`POST /v1/location/recommendations` · JSON

| 요청 필드 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `latitude` | number, -90~90 | 필수 | 위도 |
| `longitude` | number, -180~180 | 필수 | 경도 |

정의되지 않은 필드는 거절한다(422).

방이동 먹자골목에서 실제로 호출한 응답(곡은 1개만 남김):

```json
{
  "tracks": [{"track_id": "1450779337", "title": "Ohio", "artist": "HYUKOH",
              "preview_url": "https://audio-ssl.itunes.apple.com/…", "artwork_url": "https://is1-ssl.mzstatic.com/…",
              "store_url": "https://music.apple.com/…"}]
}
```

| 응답 필드 | 설명 |
| --- | --- |
| `tracks` | V1·V2와 같은 공통 `track` 객체, 0~5개. 곡을 찾지 못하면 `[]`(200) |

판정한 장소 특징과 검색어는 응답·로그 어디에도 남기지 않는다(위치를 드러내므로). 로그에는 판정 경로(`provider`)·곡 수·단계별 소요 시간만 남긴다.

| 오류 | `code` | `details.reason` |
| --- | --- | --- |
| 422 | `INVALID_REQUEST` | 없음. 좌표 누락·범위 밖·정의되지 않은 필드 |
| 503 | `SERVICE_UNAVAILABLE` | `LOCATION_CONTEXT_UNAVAILABLE`, `MODEL_UNAVAILABLE`, `MODEL_RESPONSE_INVALID`, `MUSIC_CATALOG_UNAVAILABLE`, `LOCATION_TIMEOUT` |

## 판정 규칙 요약

`backend/location/context.py`에 기준마다 근거가 된 측정값을 주석으로 남겼다.

| 항목 | 규칙 | 출처 |
| --- | --- | --- |
| 밀도 | 반경 500m 음식점+카페+편의점 수. ~10 quiet · ~150 moderate · ~500 busy · 그 이상 very_busy. 넓은 공원(2ha↑) 안이고 busy 이상이면 한 단계 낮춤 | 카카오 + OSM |
| 자연 | sea(바다·해변) · river(강·호수) · stream(계곡·개울) · forest · park. 실제 물가·숲 경계까지의 거리를 **밀도별 인정 거리**와 비교(붐빌수록 가려져 덜 보인다). 작은 공원(2ha↓)·숲(10ha↓)·연못 제외 | OSM, 바다는 카카오 해수욕장으로 보충 |
| 산 | 주변 ±1km 고도 기복 250m 이상. 봉우리 거리는 보지 않는다 | Open-Meteo 고도 |
| 산 이름 | 확실할 때만: ① 국립공원 구역 안(바다 국립공원 제외) ② 200m 안 봉우리 ③ 솟은 높이 대비 거리 점수가 낮은 봉우리. 아니면 비움 | OSM |
| 이름 | 같은 종류를 카카오도 잡았으면 카카오 한국어 이름(산 제외) | 카카오 |
| 특징 | 500m 안 관광명소 분류(테마거리·전망대·먹자골목 등), 공방 잡음 제외. 용도지역이 상업·공업이면 "업무지구" | 카카오 + OSM |

## 실험 결과

### 장소 공급자

처음 설계(위키)는 Google Places였다. 한국 좌표로 실측한 뒤 카카오 + OSM으로 바꿨다.

| | Google Places (New) | 카카오 로컬 | OSM (로컬 파일) |
| --- | --- | --- | --- |
| 밀도 | 최대 20개, 전체 개수 없음 → 번화가끼리 구분 불가 | **반경 안 전체 개수** | 없음 |
| 자연 | 유형은 있으나 사용자 등록 잡음(강남 고깃집이 `park`) | 점 하나뿐, 공원은 카테고리 없음, 강·바다는 장소가 아님 | **면·선**이라 실제 물가 거리, 면적으로 작은 녹지 제외 |
| 지역명 | 없음 (별도 유료 API) | 행정동 | 없음 |
| 비용 | 월 5,000건 무료, 이후 1,000건당 $32 | 일 10만 건 무료(카테고리 검색) | 무료, 저장 허용(출처 표기) |
| 제약 | 결과 캐시 제한 | **결과 저장 금지**, 무료 쿼터는 계정의 첫 앱에만 | 공용 Overpass 서버는 자동 호출 금지 → 파일로 받아 로컬 조회 |

### 검색어 (진행 중)

| 방식 | 결과 |
| --- | --- |
| A 템플릿 | 단어가 많아 핵심 분위기가 희석됨. 산·숲에서 힙합이 나오는 경우 |
| B-소리 (악기·템포 묘사) | 탈락. v4 어댑터가 학습한 사용자 검색어 분포 밖이고, 곡이 몰림(서로 다른 곡 115/175) |
| B-상황 (V1 `recommend_query` 형식) | 가장 다양함(151/175). 그러나 실제 `recommend_query` 3만 개보다 감성 형용사가 많음("감성" 37% vs 7%, "고요" 26% vs 0.1%), 길이 35자 vs 20자 |

- 밀도는 낮 기준 상권 규모라 밤·새벽에 "활기찬"을 붙이던 문제는 LLM 입력 필드 이름을 `daytime_commercial_scale`로 바꿔 해결(16곳 → 0곳). 대신 낮의 먹자골목에서도 활기를 피하는 부작용이 있다.
- 장소 고유명사("광안리")를 넣으면 검색어 벡터가 "바닷가 → 산"으로 바꾼 만큼 움직이지만, 광안리·해운대·강릉이 서로 다른 곡을 가져와 분위기보다 잡음에 가깝다. "산" → 산이(San E), "비" → 우산처럼 **가사·이름 단어와 맞춰지는** 현상도 보여 고유명사는 검색어에서 빼는 방향을 시험 중이다.
- 비교 페이지: `scripts/location/compare_queries.py` → `out/location/compare/index.html`

## 알려진 한계

- 검색어 방식 미확정 (위 "검색어")
- **밤의 술집거리**: 밤에는 활기를 피하라는 규칙 때문에 방이맛골도 "차분한"이 된다. 술집 비율로 `nightlife` 특징을 만드는 안을 검토 중
- **도심 뒤 산**: 황령산 아래 부산 남천동처럼 붐비는 동네도 기복이 커서 산으로 잡힌다
- 오름(성산일출봉 기복 129m)은 산으로 잡히지 않는다
- 담양 죽녹원처럼 입구 상가가 많은 숲은 체감보다 붐비게 판정된다
- 한국 OSM은 용도지역이 대부분 비어 있어 업무지구는 판교처럼 그려진 곳만 잡힌다
- 서울 밖 강가처럼 이름 붙은 시설이 없는 물가는 OSM에 의존한다
- 서버 OSM은 첫 요청 때 157MB 파일을 메모리에 올린다. 배포 방식은 논의 필요([02](02-팀-논의-제안.md))
