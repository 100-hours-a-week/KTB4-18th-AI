# 평가 지표와 계산식

기준 버전: `initial-metrics-20261031-v2` / LLM 루브릭: `20261031-reviewed-v3`.
계산식과 채점 기준은 기존 평가에서 유지했다. 구현은 grading/scoring.py, grading/metrics.py, grading/judging.py, compare.py에 있다.

## 점수를 읽는 공통 규칙

- 사례는 단일 요청 또는 여러 턴의 대화다. 각 턴의 검사를 먼저 수행한다.
- 코드 검사 결과는 원칙적으로 통과 1, 실패 0이다. 기대값 누락은 검사하지 않고, null 기대값은 실제 null을 요구한다.
- `scored`인 값만 개별 지표 평균에 넣는다. `not_applicable`과 `insufficient_evidence`는 0점으로 채우지 않는다.
- 사례의 개별 지표 = 해당 사례의 모든 턴에서 채점된 검사 점수 합 ÷ 그 검사 수.
  LangSmith 사례 평균과 compare의 검사 전체 합계/분모는 가중 방식이 다르므로 구분한다.
- 전체 점수를 하나로 합산하지 않는다. 기능, 품질, 시간, 비용을 각각 비교한다.

예: 한 대화에서 조건 검사 4개 중 3개 통과라면 조건 추출 정확도는 3/4이다.
다른 대화가 1개 중 1개라면 사례 평균은 (0.75+1)/2=0.875, 검사 전체 합계는 4/5=0.8이다.

## 코드로 채점하는 지표

아래 비율의 분모는 전체 데이터 수가 아니라 해당 지표를 실제 검사한 수다.

| 지표 / 내부 키 | 사례 안 계산식 또는 판정 |
| --- | --- |
| 요청 완료율 / 대화 완료율 (`case_completion`) | 예정된 모든 턴이 실행되고 각 턴에 done이 있으며 error가 없으면 1, 아니면 0. 전체 비율은 완료 사례 수 ÷ 전체 사례 수 |
| 의도 분류 정확도 (`route_acc`) | 실제 경로가 허용된 기대 경로에 포함된 검사 수 ÷ 경로 검사 수 |
| 조건 추출 정확도 (`slot_acc`) | 연도 하한/상한, 요청 곡 수, 비음악 요청 포함 여부, 장르, 응답 스타일의 통과 수 ÷ 해당 검사 수 |
| 조회 정확도 (`lookup_acc`) | 기대 곡 ID, 가수, 제목에 관한 통과 수 ÷ 조회 검사 수 |
| 명시 조건 충족률 (`constraint_ok`) | 반환 카드의 연도 하한/상한과 장르가 모두 조건에 맞는 검사 수 ÷ 해당 검사 수. 카드가 없으면 해당 없음, DB 근거가 없으면 판정 불가 |
| 요청 곡 수 준수율 (`cards_ok`) | 실제 카드 수 = 데이터에 지정된 기대 카드 수이면 1. 사례의 값은 해당 검사 평균 |
| 이전 곡 제외율 (`exclusion_ok`) | 이번 카드 ID와 이전 턴 카드 ID의 교집합이 비어 있으면 1. 제외 검사 지정 및 이전 카드가 있을 때만 적용. 정확한 곡+가수 재조회와 카드 없는 턴은 해당 없음 |
| 일반 텍스트 형식 (`format_ok`) | 정규식으로 Markdown 구조가 발견되지 않으면 1. 모든 정상 턴에 적용 |
| 안내 장르 일치 (`claim_ok`) | 안내가 특정 장르를 주장하면, 각 주장에 대해 해당 DB 장르 카드 수 ÷ 반환 카드 수가 0.4 이상일 때 1. 장르를 말하지 않거나 못 찾았다고 안내한 경우, 조회 응답은 제외 |
| 곡 중복 방지 (`unique_track_ratio`) | 고유 track_id 수 ÷ 카드 수 |
| 가수 다양성 (`artist_diversity`) | 고유 artist 문자열 수 ÷ 카드 수 |

장르 추출 검사는 추출 장르가 비어 있지 않고 허용 장르의 부분집합인지 확인한다.
반환 카드 조건은 각 곡의 DB 메타데이터로 별도 검사한다. 안내 장르 일치는 지정된 6개 장르 표현에 대한 휴리스틱이며 음악 적합성을 증명하지 않는다.
조회 정확도, 형식, 장르 주장, 다양성 등의 세부 값은 코드 판정에 존재하지만 모두 독립 LangSmith 열로 발행되지는 않는다.
비교 보고서는 검사별 점수 합과 분모를 따로 표시한다.

### 기능 요구 충족률 (`contract_pass`)

사례마다 다음 순서로 결정한다.

1. 예정 턴 미완료, 서비스 오류 또는 적용된 기능 검사 중 실패가 하나라도 있으면 0.
2. 실패는 없지만 근거 부족으로 판정할 수 없는 기능 검사가 있거나 적용 검사 자체가 없으면 값 없음.
3. 나머지 적용된 기능 검사가 모두 통과하면 1.

대상은 경로, 추출 조건, 조회, 곡 수, 이전 곡 제외, 형식, 장르 주장, 반환 조건, 사진 판정이다.
사진 판정 제한시간, 다양성과 LLM 품질 점수는 이 종합 기능 판정에 합산하지 않는다.
compare 보고서의 기능 요구 충족은 공통 사례 중 contract_pass=1인 사례 수 ÷ 공통 사례 수다.
값 없음도 통과 건수에는 포함되지 않으므로 개별 지표의 분모 제외 규칙과 구분한다.

## 사진, 음성, 장애 지표

| 지표 | 계산식 또는 판정 |
| --- | --- |
| 이미지 입력 판정 정확도 | usable 기대값과 실제값이 일치한 턴 수 ÷ 예정 턴 수. 기존 구현은 사진 후속 대화까지 예정 턴에 포함 |
| 구조화 응답 성공률 | scene 값이 있는 턴 수 ÷ 예정 턴 수 |
| 사진 판정 제한시간 (`verdict_in_deadline`) | verdict_ms가 데이터의 verdict_deadline_s × 1000 이하면 1 |
| 전사 성공률 | 전사 호출이 예외 없이 끝나면 사례 점수 1. 전체는 성공 사례 수 ÷ 음성 사례 수 |
| 문자 오류율(CER) | 정규화한 정답과 전사의 편집거리 ÷ 정규화한 정답 글자 수. 성공한 전사의 사례별 CER을 평균하며 길이 가중은 하지 않음 |
| 장애 처리 통과율 | 지정된 모의 pytest가 종료 코드 0이면 1. 전체는 통과 사례 수 ÷ 장애 사례 수 |

CER 정규화는 NFKC, casefold, 영숫자만 남기기 순서다. 편집거리는 삽입+삭제+치환의 최소 횟수이며 CER은 1을 넘을 수 있다.
장애 검사는 실제 공급자의 가용성 측정이 아니다. 사진 보조 판정에는 조명과 거절 사유 검사도 포함될 수 있다.

## LLM이 채점하는 지표

대상은 오류 없이 완료되고 카드가 있는 턴이다. 판정 실패는 0점으로 바꾸지 않는다.
각 사례의 지표는 채점 성공 턴에서 null이 아닌 점수의 합 ÷ 그 점수 수다.

| 지표 | 턴 점수 |
| --- | --- |
| 응답 요구 준수율 (`response_compliance`) | 요청과 유지/변경 조건을 준수하면 1, 위반하면 0 |
| 안내 근거 충실도 (`faithfulness`) | 근거 없는 사실 단정이나 자료와 모순이 없으면 1, 있으면 0 |
| 안내 적절성 (`explanation`) | 0 무관/모순, 1 모호/핵심 누락, 2 적절하고 유용, 3 간결하고 구체적 |
| 장면 해석 (`scene_accuracy`) | 0 주된 내용 오류, 1 중요한 오류, 2 사소한 부정확성, 3 원본에 근거 |
| 검색 문장과 설명 일관성 (`scene_consistency`) | 0 모순, 1 큰 불일치, 2 경미한 누락, 3 일관 |
| LLM 채점 완료율 | 채점 status=ok인 턴 수 ÷ LLM 채점 대상 턴 수 |

사진이 없거나 올바른 판독 불가 거절이면 사진 품질 두 점수는 null이다.
compare의 근거 충실도는 양쪽 모두 판정 성공인 공통 턴에서 1점 건수/턴 수를 비교한다.
장면 해석은 같은 조건의 공통 턴 점수 평균을 비교한다. 안내 적절성, 응답 요구 준수율, 일관성은 저장되지만 기본 비교 표에는 표시되지 않는다.
모델, 상세 루브릭, 가격과 출력 설정은 grading/judging.py에 고정되어 있다. 음악 청취 적합성은 이 점수에 포함하지 않는다.

## 곡 반복, 시간, 비용

| 지표 | 계산식과 범위 |
| --- | --- |
| 최다 곡 반복 비율 | max(곡별 등장 사례 수) ÷ 카드가 있는 사례 수. 한 사례 안의 같은 곡은 1회로 셈 |
| 첫 안내 대기 | 라우터 호출 시작부터 첫 text 이벤트까지의 ms ÷ 1000 |
| 추천 카드 대기 | 라우터 호출 시작부터 tracks 이벤트까지의 ms ÷ 1000 |
| 전체 처리 시간 | 라우터 실행과 스트림 소비 종료까지의 ms ÷ 1000. 추가 카탈로그 검증 시간은 제외 |
| 정상 거절 시간 | 올바르게 판독 불가 거절한 턴의 전체 시간 평균 |
| 서비스 비용 | 서비스 모델 호출들의 usage.cost 합. 한 건이라도 비용이 없거나 호출 기록 자체가 없으면 사례 비용은 미확인 |
| 요청당 비용 | 기능별 최종 사례의 서비스 비용 합 ÷ 실제 기록된 요청 턴 수. 비용 미확인이 있으면 계산하지 않음 |
| 서비스 비용 총합 | 서비스 시도 기록의 확인된 비용 합. 재시도 포함. 누락 건수를 함께 표시하며 미확인을 0달러로 간주하지 않음 |
| 평가 비용 | 해당 사례의 LLM 채점 비용 기록 합. 실패와 재개 전 시도의 확인 가능한 비용도 포함 |

LangSmith의 사례별 시간은 해당 사례에서 시간이 기록된 턴의 평균이다.
비교 보고서는 양쪽 모두 성공했고 카드가 있는 공통 턴만 골라 중앙값과 p90을 계산한다.
p90 = 오름차순 정렬한 n개 값 중 ceil(0.9×n)번째 값. 중앙값은 가운데 값 또는 가운데 두 값의 평균이다.
빠른 거절/질문을 추천 지연과 섞지 않으므로 카드 없는 응답의 속도는 기본 비교 표에서 빠진다.
시간과 요청당 비용은 최종 시도 기준, 서비스 비용 총합은 재시도 포함 기준이다.

telemetry의 generation API 보충 비용은 별도 호출 기록에 남지만, 이미 저장한 사례 비용에 소급 반영되지 않는 기존 제한이 있다.
따라서 보충된 호출 기록과 비교 표의 비용 누락을 구분한다. 이번 구조 정리에서 비용 계산 정책은 변경하지 않았다.

## dev 전후 비교 시 조건

같은 데이터, 첨부, 평가 코드, 모델/루브릭, DB, 실행 범위와 동시성으로 이전 dev SHA와 새 dev SHA를 실행한다.
서비스 모델이나 검색 설정을 의도적으로 바꾼 경우에만 `--vary`로 밝힌다.
비교는 코드 검사를 같은 규칙으로 재계산하고, 개선/회귀 사례 ID와 실제 검사 분모를 표시한다.
평가 코드 해시가 다르거나 미완료/서비스 실패가 있으면 기본 비교는 차단된다. `--allow-incomplete`는 제한된 참고용이다.
자동 배포 승인 기준이나 통계적 유의성 판정은 제공하지 않는다. 결과를 보고 사용자가 판단한다.
